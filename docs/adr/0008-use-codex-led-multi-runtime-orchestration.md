# ADR 0008: Use Codex-led multi-runtime orchestration

- Status: Accepted

The main orchestrator uses open-source Codex CLI plus public plugin, MCP, and hook extension points as its default product structure. It delegates bounded Logic Work Items through a provider-neutral runtime port to authenticated Codex CLI and Claude Code CLI workers. Codex SDK or App Server integration may be added behind the same port when its compatibility and operational benefit are proven; it is not the default and does not justify a Codex fork. Each official CLI owns its credentials and subscription metering, provider sessions are never resumed across a different backend, and ORCA is an interoperability option rather than a product dependency. Workers edit isolated worktrees and return Change Bundles; the main thread revalidates each Bundle from sidecar state, rejects overlapping Code Symbol changes, applies accepted patches in dependency order to a dedicated Git worktree, and binds full verification to the resulting integrated revision. Low-risk work requires deterministic verification; medium-risk work uses one implementation provider and the other eligible subscription runtime as a read-only reviewer; Codex-led high-risk planning assigns implementation to Claude and final review to non-author Codex. Reviewer output becomes sidecar-owned Review Findings and a Verification Run rather than caller-supplied completion evidence. The main thread owns these integration, review, and final completion decisions rather than feature-code authorship.

Runtime scheduling is an explicitly invoked asynchronous sidecar operation. The enqueue call durably records private, digest-checked job input before returning, after which workers may continue modifying their approved isolated worktrees and consuming the selected CLI subscriptions. The main thread polls the job contract for terminal state and must not interpret enqueue acceptance as completion. If the owning sidecar process stops, unfinished jobs become `interrupted`; they are not silently resumed because their context, lease, and provider session may no longer be current.

Cancellation is also durable and provider-neutral. A cancellation request moves active work to `cancelling`, propagates an abort signal to every active scheduler attempt and CLI child process, and becomes `cancelled` only after those attempts settle and their write leases are released. Concurrent completion and cancellation updates are serialized across sidecar processes so exactly one state transition wins. A process death while stopping work is `interrupted`, not a false claim that cancellation completed.
